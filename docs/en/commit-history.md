# Commits, branches and releases

::: warning v0.4 Beta
This page describes the project repository model in `v0.4.0-beta.1`. Use the isolated [Beta environment](deployment.md#beta-channel). Never connect Beta to the stable database or object store. Existing content and public links keep their compatibility read paths.
:::

## Every save creates history

The server generates revision identifiers. Save an OpenAPI, Markdown or TXT document to create an immutable commit containing its parents, author, time, message and complete file tree. Neither users nor MCP clients need to supply a version number.

A branch can receive successive commits. Content corrections, line-ending changes and file moves remain visible in history; an unchanged tree does not create an empty commit. An optional commit message explains the change and is not a revision identifier.

Each project is one repository. A branch contains the project's files, so a single commit can update both an API definition and its integration guide. History supports reading and downloading exact content, comparing commits and reverting changes.

## Initialize an existing project

A project administrator initializes the repository from the workbench. Existing published snapshots and still-available draft snapshots retain their provenance. Document branches with the same name are not treated as evidence of an earlier atomic project commit.

Inspect the imported files, branches and publications. Existing links continue to resolve their exact original objects rather than silently following a new HEAD. Overwritten draft bodies cannot become historical snapshots unless their content can still be verified.

Initialization switches the write model. Subsequent changes append commits. Older clients should upgrade to the commit tools; legacy draft writes must not continue overwriting content after conversion.

## Branches and concurrent saves

Editing captures a commit and branch generation. A save includes that baseline. If somebody else has advanced the branch, the server reports a conflict while the workbench retains your changes. Compare, merge or create another branch before saving; do not replace the current tree with an outdated full copy.

Feature branches support independent work. A merge request binds exact source and target commits. Further changes require reviewing the new result. Three-way merge conflicts need explicit resolution; AI suggestions do not silently choose a side.

## Comparisons and AI

Comparisons use exact commits rather than moving branch names. Text diffs preserve line numbers, line endings and exact downloads. OpenAPI may also include semantic changes and Breaking Change checks. A source change with identical semantics is still a valid historical commit.

AI analysis and questions bind a commit or a fixed commit pair. If C3 appears while C1→C2 is being analyzed, the answer still belongs to C1→C2. This Beta runs analysis on explicit request and retains the input fingerprint, model and status. It does not automatically generate or apply file patches. Model failures do not discard saved content.

Beta comparisons accept up to 100 changed files and 8 MiB of combined source text; larger comparisons return an explicit error. AI evidence includes up to 32 changed documents and 128 KiB, with an explicit truncation flag. Omitted evidence must not be treated as unchanged content.

## Review and publication

Saving, merging and publishing are separate operations. Administrators review exact changes and publish explicitly. Publication identifiers are generated by the server too; correcting a document does not require typing another version number. Public consumers read published content, not any unpublished HEAD.

Content lives in immutable commits, while reviews and releases reference those commits. MCP can submit changes, compare them and open merge requests, but cannot bypass human publication.

Existing public links retain their password, expiry and revocation rules. Fixed links select a document in an exact publication; later commits cannot overwrite that shared content.

## Events and subscriptions

Commits, branch changes and publication produce durable events. Consumers deduplicate by event ID and use reference generations to determine order. Failed AI or delivery work can be retried without undoing an accepted commit.

Project administrators manage subscriptions. They default to publication events and can explicitly include internal commit events. In-app subscriptions appear in the administrative delivery ledger. Webhook consumers should verify signatures and handle repeated or out-of-order events; failed deliveries can be inspected and retried.

“Git-style” describes immutable commit graphs, branches and merge semantics. It does not claim native `git clone` or `git push` protocol support.
