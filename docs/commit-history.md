# 提交、分支与发布

::: warning v0.4 Beta
本页介绍 `v0.4.0-beta.1` 的项目仓库模型。请使用独立的 [Beta 环境](deployment.md#beta-channel)，不要让 Beta 连接稳定环境的数据库或对象存储。旧版工作区及公开链接保留兼容读取路径。
:::

## 每次保存都留下提交

文档的修订号由系统自动生成。编辑 OpenAPI、Markdown 或 TXT 后选择“保存并提交”，系统创建不可变提交，保留父提交、作者、时间、说明和完整文件树。用户与 MCP 不需要填写版本号。

同一分支可以持续产生提交。内容修正、换行变化或文件移动都能保留历史；相同内容不会重复制造空提交。可选的提交说明用于解释改动，不是修订标识。

一个项目对应一个仓库。分支包含项目内文件，一次提交可以同时更新接口定义与接入说明。提交历史可以打开某次正文、下载原文件、比较两个提交或还原已有改动。

## 初始化已有项目

项目管理员在仓库入口执行初始化。系统保留旧已发布快照及仍存在的草稿快照，并记录各自来源；旧文档分支不会仅因为名字相同就被当成同一次项目提交。

导入后检查文件、分支和发布内容。旧链接仍按旧的明确对象读取，不自动跳转到新分支 HEAD。被覆盖且已无法核实正文的草稿保存记录不能恢复为内容历史。

初始化是模型切换。切换后的内容写入走追加提交，旧客户端应升级为新的提交工具；不能继续通过旧草稿接口覆盖内容。

## 分支和并发保存

编辑时固定读取的提交及分支 generation。保存请求携带该基线；如果其他人已推进分支，系统返回冲突，保留本地修改。先比较变化，再合并或新建分支，不要用旧全文覆盖最新内容。

功能分支可以独立编辑。合并请求绑定明确的来源与目标提交；目标或来源继续变化后，需要重新审阅最新结果。三方合并遇到冲突时必须解决，AI 建议不会替你静默选择一侧。

## 比较和 AI

比较选择具体提交，不依赖会继续移动的分支名字。文本差异保留行号、换行和下载内容，OpenAPI 可附带语义变化与 Breaking Change 检查。原文改变但语义相同仍然是一条有效提交。

AI 分析与提问绑定一个提交或固定的提交对。例如分析 C1→C2 时出现 C3，结果仍属于 C1→C2。当前 Beta 由用户手动请求分析，结果保留输入指纹、模型和状态；不自动生成或应用文件补丁。模型失败不会丢失已保存内容。

Beta 比较最多处理 100 个变化文件和累计 8 MiB 原文，超过限制明确返回错误。AI 证据最多包含 32 个变化文档和 128 KiB 内容，并标明是否截断；截断不表示省略内容没有变化。

## 审核和发布

保存、合并和发布是不同操作。提交内容后，管理员审阅固定改动并人工发布。发布号也由系统自动生成；不需要为了修正文档手填新的版本号。公开消费者读取明确发布的内容，而不是任意未发布的 HEAD。

发布与旧版草稿的状态流转不同：正文只存在于不可变提交中，审核和发布引用该提交。MCP 可以提交、比较和发起合并请求，不能绕过人工发布。

已有公开链接继续遵守密码、过期和撤销规则。固定链接指向固定发布中的文档；新提交不会悄悄改写已分享内容。

## 事件与订阅

提交、分支变化和发布产生持久化事件。订阅者按事件 ID 去重，引用 generation 用于判断先后。AI 和投递任务失败可以重试，不能使已成功保存的提交消失。

订阅由项目管理员管理，默认只选择发布事件；显式配置后可监听内部提交事件。站内订阅显示在管理投递记录中。Webhook 接收方应验证签名并处理重复或乱序事件，失败可查看和重试。

这里的“Git 风格”指不可变提交图、分支和合并语义；不表示已经支持原生 `git clone` 或 `git push` 协议。
