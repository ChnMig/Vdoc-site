# 文档独立分支与递增版本

日期：2026-11-01。目标版本：v0.4.0-beta.2。

本次用户确认的模型取代 `GIT_VERSIONING_REDESIGN.md` 中“整个 Project 共用分支”的设计：项目组织文档；每份文档独立拥有分支、提交历史、审核和发布。

## 用户流程

- 新建文档时初始分支默认 `main`，可手动输入其他名称；不继承当前另一篇文档的分支。
- 打开文档后，标题下提供文档分支与版本选择、新建分支。左侧项目目录不随分支变化。
- 每次有变化的保存形成不可变提交，显示 `<分支名>.<递增整数>`。每份文档的每个分支独立计数，从 1 开始。原样重试返回原版本；失败或无变化不消耗编号。
- 新分支可以从当前历史版本创建；第一次新提交为新分支的 `.1`，来源历史仍可追溯。
- main 默认可编辑；人工发布固定提交。发布和分享不跟随后续保存变化。
- 日常任务突出阅读、编辑和历史；比较、分支协作、AI、发布等保持可发现，但不要求用户先理解完整提交图。

## 数据与兼容

- 分支、提交、比较、合并和版本必须限定当前文档，后端拒绝跨文档引用或写入。
- 编号分配、提交落库、分支推进和幂等结果在同一项目事务内完成，并保留 HEAD/generation 并发检查。
- 保留原项目提交、旧版本、旧草稿和分享记录，新增文档级投影与来源记录；不重写旧正文或伪造丢失历史。
- 内部 `legacy/...` 快照引用留在历史兼容入口，不进入正常文档分支列表。
- MCP/Skill、API 文档、前端和发布资产同步新契约。

## 验证场景

1. 两篇文档均有 main/dev，互不共享分支、正文、计数或编辑状态。
2. 默认 main 和手填初始分支均能创建，首次提交为 `.1`，继续保存递增。
3. 重试、并发、失败、无变化与分支派生不会重复编号或覆盖历史。
4. 新建文档后目录可见；切分支、切文档、返回历史、刷新与移动端均可正常操作。
5. 已有 beta 数据及旧版本/分享保持可读；新模型的发布、比较、AI 和 MCP 正常。
6. 通过服务端、客户端、跨仓库契约和实际浏览器验证后发布协调 beta。
